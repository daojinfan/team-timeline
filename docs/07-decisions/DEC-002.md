# DEC-002：批准 V2 测控计划与人工执行闭环

## 状态

active，版本 1.0，归属变更后基线 BL-003。该状态表示决策已经批准，不表示 BL-003 已经激活；BL-003 激活前不授权开发或数据库迁移。

## 背景

V1 已提供本地桌面的任务、甘特图、负载、日志和备份。超导量子计算测控组还需要承接其他小组需求，在样品编号未知时按型号提前安排测试项、人员和制冷机，并对预计到样变化、执行成果和人工验收形成轻量、可追溯闭环。繁琐实验需求单、AI 自动规划和替换 V1 都不符合批准边界。

## 决策

1. V2 继续采用本地桌面、单用户、无 AI 的产品边界；所有正式任务、分配、改期选择和验收结论由人作出。
2. 采用轻量“测控计划”作为业务核心；来源小组及联系人形成业务上下文，项目/课题仅为可选标签。
3. 样品型号足以提前规划；正式或临时编号可在到样后补录，实际到样不自动开始或分配任务。
4. 预计到样和计划制冷机允许直接修改，保存前影响预览、保存后追加历史；ETA 只选择性平移用户勾选的未开始且到样后执行任务。
5. 采用工作台、测控计划、人工分配、执行、验收、管理六区桌面 IA；无移动端。
6. 主状态由事实计算，默认到样关注窗口为 7 个自然日；实际到样但尚未测试时主状态空白并排除到样窗口统计。
7. 任务采用人工分配；冲突只提示，不自动换负责人或自动调度。
8. 成果只保存说明、业务提交人、时间、URL/本地路径和清单快照；通过或退回必须由人确认，不托管二进制附件。
9. V2 通过版本化增量 schema 扩展 SQLite；迁移前备份、事务执行、失败停止、可恢复回滚，已有库不重置、不猜测回填。
10. V1 任务、甘特图、负载、日志、备份、API、CSV 和 JSON 继续兼容；V2 API 只追加，既有任务可不关联计划。
11. schema、API、DOM、状态机、冲突算法、迁移与测试以 ARC-COMP-004 的 canonical body 为冻结实现契约。

## 后果

- 获得来源、到样、制冷机、人工排期、成果与验收的一致业务闭环。
- 实现必须承担真实 V1 数据迁移、reset/软删兼容、稳定错误、桌面双尺寸和回滚验证成本。
- 人工确认记录是业务声明，不构成身份认证；URL 受协议白名单约束，本地路径只作文本。
- 状态颜色不持久化，避免窗口偏好反写业务事实。

## 未采用方案

| 方案 | 结论 | 原因 |
| --- | --- | --- |
| 继续只用 V1 描述字段承载全部上下文 | 不采用 | 来源、到样漂移、资源和验收难以检索与审计 |
| 完整实验需求单和强制项目层级 | 不采用 | 流程过重，违背轻量计划和可选标签 |
| AI 自动生成计划、任务或分配 | 明确排除 | 违背无 AI 和人作决定的批准边界 |
| 自动平移全部任务或自动换负责人 | 明确排除 | 会改变执行中事实并绕过人工确认 |
| 重建数据库或替换 V1 | 明确排除 | 破坏已有数据、接口与连续性 |

## 基线门

BL-002 禁止承载 V2 schema 开发或迁移。PM 必须创建与已批准文档及最终详设指纹一致的 BL-003，登记并激活该基线，生成 V2 工作包与上下文路由，并通过 Release 0 error/warning，之后才可 Plan/Start 开发任务。
