# 当前版本固定周期排期模式详设

## 1. 设计目标

在当前主界面中，为所有可编辑的“开始日期 + 结束日期”区间提供可选的固定周期模式。用户只修改区间的一端时，系统自动按照原有周期计算另一端，避免手工维护两个日期造成周期长度变化。

本设计以当前版本的统一工作区为唯一业务口径，不按 V2、V3 或其他历史版本拆分功能。历史接口和隐藏兼容界面只承担数据兼容责任，不新增版本专属规则。

## 2. 工作区配置

配置位置：资源维护 → 工作区偏好 → 工作区默认值。

新增配置项：`固定周期模式`。

| 配置值 | 行为 |
| --- | --- |
| 关闭（默认） | 开始日期和结束日期独立编辑，保持现有行为。 |
| 开启 | 编辑任意日期区间的一端时，另一端按当前区间周期自动调整。 |

配置沿用现有浏览器本地偏好存储键 `teamTaskGantt.v5Prefs.v1`，字段为 `fixedCycleMode: boolean`。缺失、非法或旧偏好数据按关闭处理，不影响任务数据加载。保存默认值会立即更新当前页面中的配置状态；现有“恢复全部状态”按钮仍只恢复两组状态筛选，不改变固定周期开关。

当前实现的“工作区默认值”是当前浏览器范围的界面偏好，不写入任务、事件或 SQLite，也不通过 API 传输。

## 3. 周期定义与计算规则

周期采用包含首尾日期的自然日天数：

```text
duration = daysBetween(start, end) + 1
```

当固定周期模式开启且原区间完整、合法时：

```text
修改开始日期：结束日期 = 新开始日期 + duration - 1
修改结束日期：开始日期 = 新结束日期 - duration + 1
```

示例：2026-09-03 至 2026-09-09 为 7 天；开始日期改为 2026-09-10 后，结束日期自动变为 2026-09-16；结束日期改为 2026-09-20 后，开始日期自动变为 2026-09-14。

### 3.1 编辑状态

- 每个日期区间编辑容器独立保存周期长度，避免任务区间和成员区间互相串联。
- 打开表单时，如果两端均有合法值，初始化该区间周期。
- 首次新建且只有一端日期时无法推导周期，不自动填另一端；保存时仍按原有校验处理。
- 用户清空一端时暂不改写另一端；重新输入合法日期后继续使用已记录的周期。
- 开关关闭时不自动改写日期。
- 单个日期字段（例如 ETA、到样日期）不是区间，不参与固定周期计算。

### 3.2 同步行为

任务整体区间、成员个人区间分别保持自己的周期。现有“同步全部成员/同步测试人员时间”操作仍按当前界面语义把任务区间写入选中成员，不改变固定周期模式的定义；写入后成员区间以同步得到的新区间重新计算周期。

## 4. 覆盖范围

当前主界面以下入口统一接入该规则：

1. 任务全量编辑中的计划开始/结束日期。
2. 任务全量编辑中的每位参与成员开始/结束日期。
3. 任务摘要编辑中的计划开始/结束日期。
4. 任务摘要编辑中的每位参与成员开始/结束日期。
5. 执行中心任务整体排期。
6. 执行中心成员排期。
7. 执行中心排期对话框（任务模式和成员模式）。

所有入口继续使用原有预览、冲突确认、版本校验和保存 API；固定周期只负责编辑态日期联动，不绕过服务端校验。

## 5. 交互与提示

- 工作区默认值中显示说明：“开启后，修改开始或结束日期会按当前周期自动调整另一端。”
- 自动调整不弹出确认框，用户可在保存前直接再次修改日期。
- 原有的日期错误、冲突提示和版本冲突提示保持不变。
- 保存成功后，刷新任务树、执行中心和成员排期视图，确保所有投影显示同一份任务事实。

## 6. 兼容与安全

- 不修改数据库结构，不新增版本字段，不改变既有 API 请求格式。
- 旧浏览器偏好缺少 `fixedCycleMode` 时安全回退为关闭。
- 服务端仍拒绝空区间、开始晚于结束和其他业务约束；客户端自动推导失败时不会静默提交非法日期。
- 只对当前主界面实际可用的区间编辑控件实施规则，历史隐藏兼容界面不作为独立版本验收对象。

## 7. 验收标准

- 能在工作区默认值中打开/关闭固定周期模式，并在刷新页面后保留配置。
- 开启时，当前主界面每个覆盖范围入口修改任一端，另一端按原周期自动调整。
- 关闭时，日期输入不被自动改写。
- 跨月、跨年和单日区间计算正确。
- 空日期、非法区间、冲突确认、保存和刷新行为无回归。
- 旧偏好数据、隐藏兼容接口和现有状态默认值继续正常工作。
