# V2 总体设计草案：测控计划与人工执行闭环

## 文档状态与批准门

本文是 V2 总体架构候选，不是 active 权威设计，不替代 `ARC-OVERALL-001`，也不授权详细设计或实现。当前活动基线仍为 BL-002。只有人类明确确认本总体设计并形成可审计批准记录后，项目经理才可起草详细设计；详细设计再次获得确认后，方可建立 V2 实施工作包或任务。

本文有意不规定表 DDL、迁移 SQL、API 路径/字段和控件级交互，这些属于详细设计门后的内容。

## 设计目标与原则

V2 将现有桌面任务与甘特图工具扩展为适合“超导量子计算测控组”的计划、排期、执行、成果和验收闭环，同时遵循：

- 人作决定：无 AI，正式任务、负责人、协作者、日期、改期选择和验收结果均由人确认。
- 轻量入口：以测控计划承载必要上下文，不引入繁琐实验需求单或强制项目层级。
- 到样前可规划：样品型号足以提前建立测试项、任务和资源排期；编号允许到样后补录。
- 直接修改但完整留痕：预计到样和制冷机可直接改，影响先预览，确认后自动记录历史。
- 增量兼容：保留 V1 单体架构和全部现有能力；不重置已有 SQLite，不破坏既有 API、CSV 或 JSON。

## 系统上下文与范围

系统继续作为本地单用户桌面 Web 应用运行：原生 HTML/CSS/JavaScript 客户端通过 Node.js 原生 HTTP 服务访问本地 SQLite。V2 不增加 AI、账号体系、云服务、实时协作、新网络信任边界或移动端。

来源小组的负责人、我方对接人、提交人和验收人是业务记录，不构成经过认证的用户身份。成果 URL 与本地路径按文本引用保存，服务不托管二进制文件。

## 领域层级

```text
来源小组
└─ 测控计划（可选项目/课题标签）
   ├─ 样品信息（型号；正式/临时编号可后补）
   ├─ 到样预测、实际到样与确认历史
   ├─ 计划制冷机与资源变更历史
   ├─ 结构化测试项
   │  └─ 人员任务与排期（人工创建、人工分配）
   └─ 成果提交
      └─ 人工验收记录（通过或退回）
```

项目与课题不作为父实体约束测控计划，只提供可选标签、筛选和分组。来源小组建立业务上下文，但计划仍可独立归档和查询。

## 桌面信息架构

| 区域 | 主要职责 | 与 V1 的关系 |
| --- | --- | --- |
| 工作台 | 测控计划总览列表、统计卡、关注窗口、筛选与分组、初始/当前到样漂移 | 新增 V2 聚合入口；不取代 V1 甘特图 |
| 测控计划 | 创建/编辑轻量计划、样品型号与可选编号、测试项、联系人和制冷机 | 新增 V2 领域视图 |
| 人工分配 | 主负责人、协作成员、日期、预计工时，以及负载/日期/制冷机冲突提示 | 复用并扩展 V1 任务/分配语义，最终决定仍由人作出 |
| 执行 | 任务列表、甘特图、个人进度、到样后执行标记和执行状态 | 保留 V1 任务、甘特图和负载能力 |
| 验收 | 成果说明、提交人/时间、URL/本地路径、验收清单、通过/退回 | 新增人工闭环，不存二进制附件 |
| 管理 | 来源小组、联系人、制冷机资源、窗口偏好、日志、备份与迁移状态 | 保留 V1 日志、维护、备份和恢复入口 |

详细设计需保证 1280×720 与 1366×768 桌面可用，并说明 V1 导航如何平滑进入上述信息架构；本阶段不冻结具体 DOM 或页面布局。

## 主状态分类器

总览状态由只读分类器根据事实计算，不把颜色状态写回任务或日期。优先级如下：

1. 人工验收已通过 → **已完成（绿）**。
2. 至少一个正式测试任务正在执行 → **正在测试中（蓝）**。
3. 已记录实际到样且不满足前两项 → **主状态空白**，并排除到样关注窗口统计。
4. 未到样且缺少当前确认到样日期 → **时间待确认（紫）**。
5. 未到样且本地今天晚于当前确认到样日 → **延期（红）**。
6. 未到样且当前确认到样日在 `[本地今天, 本地今天 + N 个自然日]` → **规定时间内到来（橙）**。
7. 其余未到样且有未来确认日期 → **规定时间外到来（灰蓝）**。

`N` 默认 7，可由本地桌面偏好配置。修改 `N` 只重新计算分类；初始预计到样、当前预计到样、实际到样和任务日期均不变化。“已到样待测试”从状态枚举中删除：实际到样只是一项日期事实。

## 关键业务流程

### 建立计划与到样前规划

用户选择来源小组，填写计划名称、目的、样品型号、最新预计到样、计划制冷机及结构化测试项即可建立测控计划；最新预计到样必须是一个日期或显式的“时间待确认”，计划制冷机必须选择设备或显式“待定”，不能以伪造值代替未知。对方负责人、我方对接人、项目/课题标签、正式或临时样品编号等高级信息可折叠和后补。每项正式人员任务仍需人明确创建、排期并分配，系统不得自动指派。

### 修订预计到样或制冷机

用户直接编辑当前值，系统先计算并展示：计划漂移、候选任务日期变化、人员负载变化、日期重叠和制冷机冲突。用户确认后保存新值和不可覆盖的历史记录。预计到样改变时，只把“未开始且到样后执行”的任务列为可选平移候选；默认不平移，用户逐项选择后才按日期差移动。进行中和已完成任务不可自动移动。制冷机改变不自动改任务日期。

### 到样、执行与成果

实际到样只登记日期和可选样品编号，不自动开始任务。人员按既有任务流程更新执行状态和个人进度。成果提交保存说明、业务提交人、提交时间、URL/本地路径及验收清单快照，不上传文件。

### 人工验收

验收人查看成果与清单后选择通过或退回。通过生成验收记录并使相关工作进入完成；退回保留提交历史和意见，并把对应工作恢复到可执行状态。系统不能自动通过、自动判分或用任务进度替代验收。

## 组件边界

| 候选组件 | 职责 | 不负责 |
| --- | --- | --- |
| V2 桌面工作台 | 总览查询、统计卡、筛选/分组、状态颜色和窗口偏好 | 修改业务日期、自动调度 |
| 测控计划服务 | 来源、计划、样品、测试项及计划详情一致性 | 人员自动分配、附件存储 |
| 排期与人工分配服务 | 人工任务、负责人/协作者、工时、冲突检测、选择性平移预览 | 绕过人工确认、移动进行中/已完成任务 |
| 执行适配层 | 将 V2 计划/测试项关联到 V1 任务、甘特图、负载和进度 | 改写 V1 任务语义或既有接口 |
| 成果与验收服务 | 文本引用、提交版本、清单快照、通过/退回记录 | 二进制文件托管、自动验收 |
| 历史与审计服务 | 到样/制冷机确认历史、人工操作与迁移状态查询 | 身份认证或不可追溯覆盖 |
| 兼容与迁移层 | 增量 schema 版本、事务迁移、备份、兼容验证 | 重置已有数据库、破坏性格式替换 |

上述是总体职责边界，不是实施模块或文件所有权；是否合并组件、具体 API 和事务边界须在总体设计批准后的详细设计中确定。

## 拟议增量数据实体

V2 预计在现有 schema 旁新增或可空关联以下概念，名称仅表达领域含义，不构成表名或 DDL：

- 来源小组与业务联系人。
- 测控计划、可选标签和样品身份（型号、临时编号、正式编号）。
- 结构化测试项及其与既有任务的可空关联。
- 初始/当前预计到样、实际到样及到样确认历史。
- 制冷机资源、计划选择和资源变更历史。
- 任务主负责人、协作者、预计工时和“到样后执行”属性。
- 成果提交版本、URL/本地路径引用、验收清单快照与人工验收记录。

现有任务可以不关联任何 V2 计划并继续工作。新增关联默认可空；现有记录不得被猜测、自动归类或强制回填。详细字段、约束、索引和 API 在后续详细设计中提出并单独批准。

## 迁移、兼容与回滚

- V2 采用有版本号、可重复检查的增量迁移；迁移前生成可恢复备份，并在单个事务或明确可恢复阶段中执行。
- 迁移只增加必要结构和可空关联，不重置、删除或批量改写已有成员、任务、分配、日志、模板和检查项。
- V1 页面与现有任务/甘特图/负载/日志/备份在未使用 V2 数据时行为不变；既有 API 路径、请求/响应字段和 CSV/JSON 格式保持兼容。V2 能力优先使用新增、版本化接口，具体契约后定。
- 迁移失败必须停止启动或回到只读/安全状态，不得带着部分 schema 继续写入。回滚以应用版本回退和迁移前数据库备份恢复为基础，禁止用“重置示例数据”替代迁移回滚。
- 每次迁移需要记录 schema 版本、开始/完成时间、结果和备份位置；不得记录二进制成果内容。

## 安全与数据边界

- 保持本地单用户和现有监听范围，不把业务联系人、样品信息、URL 或本地路径发送到外部服务。
- 所有用户文本在 HTML 呈现前转义；URL 需限制为批准协议，本地路径仅作为不可执行文本展示。
- 无登录意味着提交人、验收人和确认人是业务声明字段，界面和日志不得暗示已经过身份认证。
- 数据删除沿用可恢复与备份优先原则；V2 迁移、批量平移和验收状态改变必须具备审计记录。

## 总体验收

- V2-REQ-001 至 V2-REQ-016 均有自动化或桌面验收映射。
- 状态分类器覆盖优先级、7 日默认窗口、可配置窗口、延期、时间待确认、实际到样空白状态和完成覆盖。
- 选择性平移证明只改变用户勾选的未开始到样后任务，进行中/完成及未勾选任务不变。
- 人工分配证明系统不自动指派，冲突只是提示；人工验收证明通过与退回形成闭环。
- 从真实 V1 数据副本执行迁移并验证行数、关键字段、API、CSV/JSON、任务、甘特图、负载、日志与备份兼容；禁止用新空库测试替代已有库迁移验证。
- 在 1280×720 和 1366×768 验收六个桌面区域的核心路径，无手机端验收项。

## 开放问题与下一批准门

总体设计确认时请重点确认：六区桌面信息架构是否合适、主状态优先级及“已到样未测试为空白”的语义、增量实体边界、选择性平移规则和人工验收闭环。确认前详细设计保持阻塞；确认后仍需对 API、DDL、迁移、冲突算法、验收状态机和界面契约形成详细设计，并再次取得人类批准后才能创建实施任务。
