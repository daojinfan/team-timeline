# 团队项目模式规则

## 1. 适用条件

团队项目模式使用 `TEAM_PROJECT` 标识。满足以下任一条件时可以启用：

- 项目跨越多个模块或领域；
- 至少有两个可以独立验收的工作包；
- 需要多个 AI 任务并行或分阶段协作；
- 需要单独的项目经理任务维护依赖、风险和集成；
- 人类明确要求使用团队项目模式。

单文件修改、单模块小改动、普通问答、单次诊断默认使用 `SINGLE_TASK`。

## 2. 两种运行模式

### SINGLE_TASK

当前任务直接完成工作。仍必须遵循文档权威、基线、决策和变更控制规则，但不创建独立执行任务。

### TEAM_PROJECT

当前主任务是项目经理（Project Manager），是人类的唯一项目管理接口。执行工作由独立的 Codex 任务承担。

```text
人类负责人
    |
项目经理任务（唯一项目接口）
    |
需求/架构/实现/测试等独立交付任务
    |
独立审核任务
    |
集成与验证
    |
人类验收和发布批准
```

## 3. 团队项目阶段

团队项目按以下状态推进：

```text
DISCOVERY
  -> OVERALL_DESIGN_PENDING_APPROVAL
  -> DETAILED_DESIGN_PENDING_APPROVAL
  -> EXECUTION_PLANNING
  -> TEAM_EXECUTION
  -> INTEGRATION_AND_VERIFICATION
  -> USER_ACCEPTANCE
  -> CLOSED
```

同一时间只维护一个明确的项目阶段。阶段变更必须更新 `CURRENT-STATE.md`。

## 4. 设计批准门

1. 总体设计未经人类明确确认，不得进入详细设计定稿。
2. 详细设计未经人类明确确认，不得创建执行任务。
3. 人类明确说“按此执行”“开始开发”等表达可以触发批准记录流程；只有批准对象、范围和原始文本写入 `APPROVAL-LOG.md` 后，才视为授权执行。
4. 设计或范围发生重大变化时，暂停受影响的任务，更新变更包和基线后再继续。

## 5. 执行任务边界

每个独立执行任务必须有：

- 唯一的 `WP-NNN` 工作包；
- 明确的目标、范围和范围外事项；
- 当前基线和权威文档；
- 文件或模块所有权；
- 上游依赖和下游消费者；
- 验收标准和验证命令；
- 项目经理任务标识；
- 明确的任务角色；
- 独立审核任务标识、审核标准和审核证据要求；
- 明确的完成报告格式。

执行任务不得：

- 创建或协调其他项目任务；
- 扩大工作包范围；
- 静默改变已批准架构；
- 覆盖其他任务或用户已有修改；
- 未经授权推送、部署、合并主分支或发布。

## 6. 并行和冲突

1. 只有写入范围互不重叠且依赖已满足的任务才能并行。
2. 修改同一文件、公共接口、共享数据模型或公共组件时，必须指定唯一所有者或改为串行。
3. 跨模块接口必须先稳定契约，再并行实现。
4. 默认同时运行不超过三个执行任务，除非项目规则明确调整。
5. 并行完成不等于项目完成，必须经过项目经理集成和验证。

治理状态采用“单协调工作树”拓扑：项目经理指定唯一协调工作树，只有该工作树可以执行 `Plan`、`AssignReview`、`Start`、`Verify`、`RecordReview`、`RecordApproval`、`Accept` 等治理状态变更。隔离执行 worktree 只修改自己的交付范围并返回提交、差异和证据，不直接维护 `.governance/runtime`、任务台账或工作包状态；项目经理先把交付集成到协调工作树，再在那里执行验证和状态转换。编排锁按 Git common directory 共享，但锁不能代替这条单写者规则。这样可以避免不同 worktree 拥有互不一致的 TASK 状态副本。

## 7. 强制独立审核门

协调工作树中的 `Start` 必须记录项目经理的 `LeaseOwner`；活动 TASK 的 `Verify` 必须提供匹配的租约 ID 与持有者。编排锁负责互斥，持久 transaction journal 负责在进程崩溃后恢复核心状态文件，两者都不能替代单协调者规则。

1. 每个准备进入集成、验收或发布的独立交付任务，都必须由另一个独立 Codex 任务审核。人类验收、项目经理复核和交付任务自测均不能替代独立审核。
2. 交付任务开始前，项目经理必须同时在任务台账中指定审核任务。审核任务可以覆盖同一工作包内多个紧密相关的交付任务，但必须逐项给出审核结论和证据。
3. 审核者不得是交付任务本身，不得直接修改被审核任务的交付范围，也不得继续委派。发现问题时必须给出 `changes-required` 结论；原交付任务修复并重新 `Verify` 后，项目经理使用 `ReopenReview` 把原审核任务恢复到 `planned`，再重新执行审核。每轮使用新的证据文件，旧证据及其 SHA-256 保留在不可变历史中，不得覆盖。
4. 审核必须先检查本次任务从任务启动 Git 提交到当前工作树的单一净差异，识别实际新增、修改、删除或重命名内容，并在审核证据的 `changes` 中逐项列出路径、变更类型和内容摘要；`renamed` 还必须记录 `old_path`。编排器和 Strict 必须使用同一差异语义，独立确认清单与该任务写入范围内的实际 Git 变更集合及变更类型一致。没有实际变更清单不得通过。只读取自动化测试的 `pass` 输出、只复述交付任务报告或只检查证据文件，不构成独立审核。
5. 审核还必须检查范围和基线一致性、验收标准、测试及证据、设计漂移和风险标志。`diff_checked=true` 与非空 `change_summary` 是 `passed`/`changes-required` 的必要条件；自动化测试只能作为辅助证据，不能替代对新增或修改内容的审查。
6. 审核状态只允许 `pending`、`running`、`changes-required`、`provisional-passed`、`passed` 或 `cancelled`。审核轮数按任务档位执行：`Lite` 对同一最终变更内容完成一轮完整审核即可形成 `passed`；`Standard`/`Release` 的第一轮只能形成 `provisional-passed`，项目经理必须执行 `ReopenReview`，让审核任务重新经过 `Start -> Verify -> RecordReview` 并完成第二轮全量审核后才形成 `passed`。第二轮不得只检查第一轮发现项。`Standard`/`Release` 只有内容指纹未变化且连续两轮均通过才能最终通过。任一轮 `changes-required` 或两轮间内容指纹变化都会把连续通过计数清零，整改后按档位重新开始。不得通过连续调用 `RecordReview`、复用证据路径或内容、或在一次审核中提交多个证据文件伪造审核轮次。
7. `cancelled` 只适用于未进入集成且运行时已经 `superseded`、台账已经映射为 `replaced` 的任务；`archived` 仅用于运行时生命周期结束后的历史台账记录。取消审核不得作为审核豁免，团队模式不允许以项目经理决定、风险接受或人类验收替代缺失的独立审核。
8. 只有审核任务已经完成并保持运行状态 `verified`、审核状态为 `passed`、连续通过计数达到任务档位要求（`Lite=1`、`Standard/Release=2`）、内容指纹仍匹配且所需轮次证据有效时，交付任务才能标记为 `completed`、进入集成或请求人类验收。审核任务不得记录 acceptance approval 或进入 `accepted`；工作包聚合时，审核任务的 `verified` 按审核已完成处理。
9. 审核任务自身不递归要求第二个审核任务，但项目经理仍必须检查其实际审核证据。历史审核任务若已处于 `accepted`，Strict 必须拒绝；AI 应使用 `MigrateReviewer` 将其规范化为 `verified` 并重新执行 Strict，不能直接修改运行状态。

执行成员初始指令必须包含：

```text
MODE: CODEX_TEAM
ROLE: TEAM_WORKER
NO_DELEGATION: true
```

独立审核成员初始指令必须包含：

```text
MODE: CODEX_TEAM
ROLE: TEAM_REVIEWER
NO_DELEGATION: true
```

两类任务都必须同时收到工作包、当前基线、范围、依赖、权威文档、验收或审核标准、允许写入路径和完成报告格式。审核任务的 `allowed_paths` 和 `write_paths` 都只能位于自己的 `docs/05-quality/evidence/TASK-NNN/` 目录；审核任务可以通过 `read_paths` 读取被审核实现，但不得写入被审核交付范围或其他审核目录。该限制由编排器启动门和 Strict 校验双重执行。`Lite` 任务仍需独立审核，但只需一轮；`Standard`/`Release` 需要两轮。

任务契约应使用 `role`、`read_paths`、`write_paths` 和 `review.required` 表达冻结后、机器可校验的职责边界；动态审核关系不得复制到不可变契约中。成员初始指令中的 `TEAM_REVIEWER` 是协作角色名，TASK 契约中的对应机器字段值为 `role=REVIEWER`。`Plan` 必须原子创建任务台账行，普通交付任务的运行状态可以先创建为 `review.status=unassigned`，随后使用 `AssignReview` 同时写入运行时 `reviewer_task_id` 和台账审核任务字段；审核成员完成验证后使用 `RecordReview` 更新运行时审核状态、证据、连续通过计数、审核对象指纹和任务台账，不要求人工预造台账行或直接编辑 JSON 状态。契约 Schema 暂时兼容旧版 `reviewer_task_id`/`status` 字段，但它们只作为迁移期计划快照，不是当前状态来源；新任务不得再写入。

审核证据必须符合 `schemas/review-evidence.schema.json`，至少列出审核任务、被审核任务、工作包、基线、`diff_checked`、每个被审核任务的实际变更路径/类型/摘要、变更总览、检查范围、发现项和结论。证据中的工作包和基线必须与被审核 TASK 契约完全一致；`passed` 或 `changes-required` 不能只有测试输出，必须有非空实际变更清单，且 `change_type` 必须与 Git 实际状态一致。一个审核任务可以为不同被审核任务保存多个证据文件，编排器和台账必须按任务分别保存证据路径。审核者读取实现范围，但只能写入自己的审核证据目录；`read_paths` 与 `write_paths` 不得混用。

## 8. 项目经理职责

项目经理必须维护：

- 当前阶段和阶段门；
- 任务台账、依赖和任务状态；
- 决策队列和变更包；
- 风险、阻塞和设计漂移；
- 各任务的实际交付物和验证证据；
- 交付任务与独立审核任务的绑定、结论和审核证据；
- 集成顺序和用户验收材料。

启用 `TEAM_PROJECT` 时，`governance.json.authoritative_documents.task_ledger` 必须指向存在的任务台账。台账元数据必须显示 `project_mode: TEAM_PROJECT`、`ledger_status: active`，并记录有效的项目经理任务标识；否则不得进入 `TEAM_EXECUTION`。

项目经理不得只根据执行任务或审核任务的自述宣布完成，必须检查实际文件、差异、测试、审核证据和集成结果。

## 9. 人类控制点

人类至少在以下时点介入：

- 总体设计批准；
- 详细设计批准；
- 重大范围、架构、接口、数据或安全变更；
- 阶段门通过；
- 集成验证通过；
- 用户验收和生产发布。

团队模式的目标是减少人类逐项协调，而不是移除人类对方向、基线、风险和不可逆操作的控制。
