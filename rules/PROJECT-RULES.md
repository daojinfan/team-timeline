# 项目治理规则

## 1. 项目事实来源

1. 聊天内容只是探索上下文，不是项目事实。
2. 已批准的项目文档是项目的权威事实来源。
3. 文档发生冲突时，AI 必须暂停受影响的工作并报告 `needs-decision`。不得根据文件时间、文件名或个人偏好自行选择。
4. 任何约束执行的文档都必须有负责人、状态、版本和所属基线。

## 2. 项目基线

1. 每个工作包必须准确引用一个项目基线。
2. 基线是当前有效决策、需求、设计和交付约束的完整快照。
3. 变更包完成影响分析并获人类批准后才能批准新基线；批准后的基线必须通过独立激活步骤成为唯一可执行基线。
4. 基线变化后，受影响的工作包必须重新进行影响评估，不能静默改写原有范围。
5. 每个有效基线必须登记到 `BASELINE-REGISTRY.md`，并拥有包含文档版本、Git 提交和文件哈希的机器可读清单。
6. 文档 frontmatter 的 `baseline` 记录该内容最后被批准、引入或实质变更时的来源基线，不要求随项目当前基线统一改写。当前基线的完整文档成员关系以 `baselines/<基线编号>/manifest.json` 为准。

## 3. 决策治理

1. 重要决策必须拥有唯一的 `DEC-NNN` 编号。
2. 有效决策必须记录在 `docs/07-decisions/` 并登记到 `DOC-REGISTRY.md`。
3. 替代旧决策的新决策必须声明 `supersedes: DEC-NNN`，并说明影响范围。
4. 禁止直接修改旧决策来改变其含义。应将旧决策标记为 `superseded`，再创建新决策。
5. 决策状态包括 `proposed`、`approved`、`rejected`、`superseded`、`retired`。

## 4. 设计层级

项目必须维护可导航的设计层级：

```text
项目章程 -> 需求 -> 总体设计 -> 领域设计 -> 组件详设 -> 工作包 -> 验证证据
```

上层文档定义边界和意图，下层文档对其进行细化。下层实现不得静默改变上层契约。

## 5. 变更传播

每个重要变更都必须有一个 `CR-NNN` 变更包。变更包需要记录受影响的需求、决策、设计、接口、数据、工作包、测试、运行文档和发布约束。

更新顺序为：

```text
变更提议 -> 影响分析 -> 决策批准 -> 总体设计 -> 领域/详设 -> 工作包 -> 测试/证据 -> 当前状态
```

## 6. 必须由人类批准的事项

- 范围或成功标准变化；
- 总体架构和公共接口变化；
- 数据模型、数据迁移、数据删除或数据保留策略变化；
- 安全、合规或隐私例外；
- 跳过质量门禁；
- 生产部署或不可逆操作。

## 7. 完成定义

工作包范围、依赖和验收标准记录在 `WORK-PACKAGES.md`，执行状态记录在 `WORK-STATUS.md`。工作包内的日常请求由机器生成的 `TASK-NNN` 契约和状态承载，AI 负责维护，人类不手工编辑。`implemented` 表示代码或文档已经修改；`verified` 表示存在必要的工具验证证据；`accepted` 表示人类负责人已经接受结果。只有 `verified` 和 `accepted` 才计入项目进度。

## 8. 框架版本

每个项目必须在 `governance.json` 中锁定治理框架版本、源提交、源工作树是否为脏状态及源树哈希。项目 ID 必须稳定，不因显示名称或目录变化而改变。框架升级属于受控变更：升级前检查本地规则差异，升级后运行 Strict 校验，并把升级结果记录到变更包和当前状态。不得静默覆盖项目中的本地规则修改。
